## 3. 角色与核心场景

| 角色 | 核心目标 | 关键动作 | 痛点 |
|---|---|---|---|
| 学生 | 找到可信的实习/校招岗位并获得反馈 | 注册、维护简历、搜索职位、投递、查看结果 | 岗位真假难辨、投递后无反馈 |

## 5. 本期范围（MVP）

### 5.1 纳入范围

- 学生、企业、管理员三角色登录与角色隔离
- 企业资质 + 企业 HR 双审核
- 职位发布、审核、关闭、推荐
- 简历维护、附件上传、平台核查
- 职位搜索（关键词 / 城市 / 类型）
- 投递、简历快照、状态流转、反馈
- 管理端四层审核与平台概览
- REST 接口（FastAPI）与 OpenAPI 3.1 契约，本地可调用
- 自动化测试与本地可复现启动

### 5.2 排除范围

| 排除项 | 原因 |
|---|---|
| REST 接口公网托管 | Community Cloud 只运行一个 Streamlit 进程（D-02） |
| MCP / stdio 替代 REST | stdio 仅进程间通信，无法作为 HTTP 接口或 OpenAPI 契约 |
| 移动端 H5 / 小程序 | 图 1 标注为“可选”，Streamlit 响应式能力有限 |
| 邮件 / 短信通知 | 需要第三方服务，超出 MVP |
| 在线支付、合同签署 | 与校招匹配主流程无关 |
| 实时聊天、视频面试 | 技术复杂度高，偏离 Streamlit 定位 |
| 多学校 / 多租户 | 需要额外的数据隔离设计 |
| 营业执照 OCR | 需要第三方 OCR 服务 |
| 管理员自助注册 | 安全风险，改为初始化脚本创建 |

## 6. 需求冲突与取舍

| 冲突 | 取舍 | 理由 |
|---|---|---|
| “实时查看反馈” vs 无推送通道 | 页面刷新后查看 | MVP 不接消息服务；状态在页面内可见 |
| “搜索人才库” vs 隐私保护 | 企业只能搜索投递到本公司职位的候选人 | 避免简历被全平台企业随意检索 |
| “功能完整” vs 初学者可维护 | 优先主流程闭环，砍掉通知、支付、H5 | 保证能讲清、能测试、能维护 |
| “管理员审核效率” vs 合规 | 保留四层独立审核，不做一键全审 | 四层审核是案例核心特点 |
| “简历可修改” vs 企业看到一致内容 | 投递时保存简历快照 | 兼顾学生更新与企业留档 |

## 8. 需求追溯关系

```text
图 1 案例 + 补充交付要求
        │
        ▼
RQ-01 ~ RQ-28、DQ-01 ~ DQ-10（本文件）
        │
        ▼
US-01 ~ US-17（Spec 用户故事与验收标准）
        │
        ▼
T-01 ~ T-15（TDD 测试清单）
        │
        ▼
tasks.md（实施任务）→ checklist.md（验收）
```

**追溯规则：** 任一 `US-*` 必须能找到一个或多个 `RQ-*` 来源；任一 `DQ-*` 必须能在 README 的最终交付物对照表中找到文件或执行计划。
